Accessibility & Phone Readiness

An honest audit of who can comfortably use the app today — and what it takes to reach a phone in every pocket.

This report answers two questions raised in review: how accessible is the design as it stands, and what is required to ship it on phones. The score below reflects the prototype as built (tablet, landscape). It is a design-stage estimate against WCAG 2.1 AA — not a substitute for an audit with assistive tech on real devices, but enough to prioritise.

03Recommendation: an “Accessible view”

Rather than compromise the signature look for everyone, add an opt-in Accessible view in Settings → Preferences (or auto-enable when the OS signals high-contrast / large-text / reduced-motion). It re-skins via a single data-a11y attribute on the root, so the brand stays intact while the mode is active.

What it changes

  • Contrast: darker ink, solid surfaces instead of textures, AA-compliant tokens
  • Type: larger base size, normal-case labels, system/dyslexia-friendly font option, no decorative script for UI text
  • Motion: cross-fades replace flips & spins
  • Editor: the list-based placement path becomes primary; bigger handles
  • Focus: always-visible focus rings

Why this shape

  • One token layer to maintain — no parallel UI
  • Respects user OS settings automatically
  • Keeps the default experience on-brand
  • Demonstrates good-faith WCAG effort for App Store review & procurement
◐
Quick wins first (≈ a day each)

Three changes lift the score most: bump the two faint text tokens to AA, add a global :focus-visible ring, and wrap animations in prefers-reduced-motion. None touch layout. The Accessible view and editor keyboard path are the larger follow-ups.

04Phone readiness

The app is designed as a 1024×768 landscape tablet surface and most screens use absolute positioning tuned to that canvas. Phones are the majority of devices, so this matters — but the screens fall into three honest buckets:

→
Phone · portrait
EffortScreensWhat's needed
Reflows easilyLoading, Welcome, Settings, Subscription, Feedback, legal modalsAlready single-column / centred. Swap fixed widths for fluid + safe-area insets; they mostly "just work" in portrait.
Needs a portrait layoutHome shelf, Shop, Package openingRe-rack the carousel/grid vertically; move toolbars to a bottom bar within thumb reach; larger tap zones.
Needs rethinkingJournal Editor (canvas)A landscape spread can't shrink to a phone and stay usable. Options: edit one page at a time, pan/zoom a full spread, collapse the page-strip into a sheet, and float the tool drawer as a bottom sheet.

How to build it in now (so phone is possible later)

  • Replace the fixed frame with a responsive root. The .pp-frame 1024×768 box becomes min(100vw, …) with breakpoints; screens read a layout context (tablet | phone) instead of assuming width.
  • Adopt fluid units & safe areas. Move from absolute pixel offsets to flex/grid + env(safe-area-inset-*); this is the bulk of the work and pays off for every screen.
  • Design the editor for both postures up front — it's the one screen where phone isn't a reflow but a separate interaction model. Decide single-page vs. pan-the-spread before building.
  • One codebase. React Native / Expo (recommended in the Backend Guide) gives responsive primitives and real safe-area handling; the layout context maps cleanly to its dimension hooks.
