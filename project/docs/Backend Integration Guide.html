Backend & Integration Guide

From clickable prototype to a shipping app — how each screen and data model maps onto real, off-the-shelf services.

Version 1.0 Date June 2026 Scope Consumer app · Studio CMS · Backend Status For implementation

This document is the wiring diagram that sits alongside the design files. The prototypes in ui_kits/app (the consumer tablet app) and ui_kits/cms (the Studio CMS) define behaviour and data shape; this guide names the services that make them real and shows how the pieces connect. Nothing here requires building a backend from scratch — it is an assembly of four to five mature platforms, plus one piece of genuinely custom app code (the journal canvas).

Why React Native / Expo

The prototypes are already React, so screen logic and state port with the least friction, and you ship iOS + Android from one codebase. The canvas engine (§7) is the one part where you may drop to a native or Skia layer for performance.

03Content model → CMS schema

The shapes in ui_kits/cms/data.js are the schema. One Item model powers both the Shop (SCR-06) and the journal-editor drawer (SCR-07) — author once, appears in both. Pack and Collection reference items by id.

Pack — the daily delivery

Each date ships two parcels: a free list for everyone and a subscription list for members. This mirrors the two-track builder in the Studio CMS.

// Pack (one document per delivery date)
{
  date:  "2026-06-10",
  title: "Poppy Field",
  free:  [ref(tap-sage), ref(typ-date)],            // every user
  sub:   [ref(flo-poppy), ref(pnt-wash), …]      // premium members
}

Collection (the bundles sold in the Shop) is the same idea: { name, palette, price, items: ref[] }. Feedback is { type: idea|bug|love, message, email?, createdAt, read } — written by the app, read in the Studio CMS inbox.

04Read APIs the app calls

The app never sees drafts or future content — every content read filters on publishAt. A thin edge function (or the CMS's GraphQL/CDN API) serves these.

// Shop / editor library — only what is live
GET /items?status=live&category=stickers

// Today's parcel; app shows `free`, unlocks `sub` if entitled
GET /packs/today      // where date == today

// User's own journals (App DB, auth-scoped)
GET /me/journals
PUT /me/journals/:id   // each spread serialized to JSON

// Feedback from SCR-23
POST /feedback        // { type, message, email? }

05Free vs. subscription — entitlements

This is the centre of the business model and a fully standard RevenueCat pattern. Define one entitlement, premium. Everything keys off it — no custom billing code.

const isPremium = await Purchases.getCustomerInfo()
                  .entitlements.active["premium"] != null;

// Daily delivery (SCR-05 / parcel)
const items = isPremium ? [...pack.free, ...pack.sub] : pack.free;

// Ad banners (SCR-05 Home & SCR-07 Editor)
showAdBanner = !isPremium;

// Paid Shop items are free for subscribers
canUseFree = item.tier === "free" || isPremium;
♛
One flag, three behaviours

The same premium entitlement that unlocks the subscription pack also removes the ad banners and grants paid items — exactly the toggles already wired in the prototype's Settings screen.

06Scheduling & launches

Status is derived, never stored: publishAt > now → Scheduled, publishAt ≤ now → Live, empty → Draft. Stage a whole season weeks ahead and it goes live automatically — no deploy, no manual flip. Every major CMS (Sanity Scheduled Publishing, Contentful scheduled publish) supports this natively, so the Studio CMS schedule view is just a read of that data.

07The journal canvas (custom)

The one piece with no off-the-shelf answer. The editor's placing, dragging, resizing, rotating, layer reordering, page-flip, zoom and off-page clipping is a real 2D scene-graph. Budget most engineering time here.

What to build

  • A scene model: each spread = ordered list of placed items with x, y, w, h, rotate, z
  • Gesture layer (pan / pinch / rotate) on a Skia or native canvas
  • Serialize spreads to JSON → store per journal in the App DB

What you already have

  • The exact interaction spec — layers, clipping, snap, toolbar
  • The data shape for a placed item (see the prototype)
  • Cover / endpaper / texture model and the asset taxonomy
